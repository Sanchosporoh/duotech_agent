# Целевая архитектура

## Принцип

Делаем целевые компоненты сразу, но каждый компонент сначала получает простейшую реализацию. Например, источник данных сразу оформляется как отдельный адаптер, но сначала читает подготовленные CSV-файлы, а позднее — БДРВ.

## Компоненты

1. **Источник данных** — читает подготовленный набор плановых и фактических данных. В первой версии это CSV, позднее SQL-запрос к БДРВ.
2. **Контроль качества** — проверяет наличие обязательных колонок, типы данных, дубли, пропуски, временное покрытие, единицы измерения и свежесть последней записи. Проверки физической достоверности раскрываются и добавляются вместе с предметными сценариями.
3. **Почасовой мониторинг** — каждый час проверяет появление новых данных и рассчитывает отклонение на доступном горизонте. Частота запуска и правило подтверждения отклонения — разные настройки.
4. **Реестр возможностей** — читает синтетический результат внешней методики модели ограничений. Мероприятия в реестре уже прошли проверку модели. Агент не повторяет эту проверку, а применяет новые глобальные ограничения, которых в модели не было: ресурсные, экономические и организационные.
5. **Расчёт прогноза** — в первой версии вызывает постоянный, заранее проверенный код. Позднее тот же интерфейс сможет вызывать локального субагента.
6. **Оптимизация** — выбирает вариант только среди мероприятий реестра с учётом новых глобальных ограничений и целевой функции.
7. **Контроль человеком** — показывает входы, промежуточные результаты и итоговую рекомендацию; автоматической отправки режима нет.
8. **Реестр действий** — на этапе MVP создаёт запись в локальном файле задач. В финальной версии тот же интерфейс создаёт задачу в Битрикс через вебхук.
9. **Журнал прогонов** — сохраняет состояние и результаты каждого шага по `run_id`.

## Запуск

На первом этапе Windows Task Scheduler раз в час запускает команду из каталога проекта:

```powershell
.venv\Scripts\python.exe main.py
```

Это запускает обычный процесс мониторинга. Вызов LLM является отдельной операцией внутри процесса и нужен только на тех шагах, где он будет обоснован.

## Если факта нет

Отсутствие свежего факта не считается отклонением добычи. Система не запускает диагностику и оптимизацию, сохраняет статус `waiting_for_data` и проверяет данные в следующий почасовой запуск. Если задержка превышает допустимое время, появляется запись `needs_attention` для инженера. Последнее известное значение можно показывать на экране, но нельзя подставлять как свежий факт при принятии решения.

## Вызов LLM

Рабочая программа вызывает установленный Codex CLI командой `codex exec`. Прямой API модели в MVP не используется. Ответ возвращается в заданной JSON-структуре. Возможность LM Studio остаётся за рамками текущего этапа.

## Внешнее действие

В MVP агент записывает расчётную задачу в локальный файл-реестр. Это безопасный имитатор внешней системы: тесты не создают реальные задачи для сотрудников. Запись защищается ключом идемпотентности, поэтому повторный запуск не создаёт дубль.

Целевой адаптер Битрикс использует вебхук и создаёт задачу на рассмотрение изменения режима. Он остаётся выключенным до финального этапа и требует отдельного параметра `bitrix_enabled=true`.

## Будущее подключение локального субагента

Основная программа передаёт субагенту задание и получает код с результатом. Конкретный транспорт выбирается после проверки его текущего интерфейса: команда запуска, локальный HTTP-интерфейс или обмен файлами.

Для окончательной интеграции надо знать текущий интерфейс субагента: команда запуска, API-адрес или папки входа/выхода.
