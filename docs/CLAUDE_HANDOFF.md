# Передача проекта Claude Code

## 1. Зачем существует проект

Это учебный MVP агента мониторинга и оптимизации добычи. Он раз в час получает агрегированный факт сепаратора и неполную телеметрию скважин, обнаруживает отклонение от плана, диагностирует вероятные причины, ищет компенсирующие мероприятия и готовит решение инженеру.

Проект должен выглядеть как живая система, а не как заранее прописанный сценарий. Изменение входных CSV или телеметрии должно менять кандидатов, гипотезы и результат обычным алгоритмом.

## 2. Целевая цепочка

```text
План + факт сепаратора + телеметрия
                  │
                  ▼
Проверка качества и свежести данных
                  │
        отклонение больше допуска?
             │ нет          │ да
             ▼              ▼
        ждать час       открыть инцидент
                              │
                              ▼
              телеметрическое ранжирование кандидатов
                              │
                              ▼
            Codex: конкурирующие гипотезы и проверки
                              │
                              ▼
       обычные проверки + PROSPER для IPR/лифта при необходимости
                              │
                              ▼
          реестр потенциалов → выбор наборов мероприятий
                              │
                              ▼
          GAP: точные режимы, интерференция и ограничения
                              │
                              ▼
       прогноз до конца горизонта и лучшее допустимое решение
                              │
                              ▼
                  решение инженера (HITL)
                              │
                              ▼
             локальный реестр и почасовая имитация эффекта
```

## 3. Что делает LLM, а что обычный код

### LLM уместна

- формирует несколько объяснимых диагностических гипотез;
- предлагает разные стратегии выбора мероприятий: минимальное число воздействий, распределённое воздействие, технологический/геологический компромисс;
- учитывает текстовый комментарий инженера при доработке предложения;
- объясняет результат простым инженерным языком.

### LLM не нужна

- проверка схемы и свежести данных;
- расчёт отклонения, недобора и требуемой компенсации;
- физические пороги и единицы измерения;
- запуск PROSPER/GAP и чтение их результатов;
- контроль воды, забойного давления, давления в линии и других численных ограничений;
- идемпотентная запись утверждённого решения;
- повтор после недоступности лицензии.

## 4. Роль расчётных инструментов

### PROSPER

Используется для проверки согласованности состояния отдельной скважины:

- прежняя модель лифта/насоса объясняет текущие давление и дебит или нет;
- изменение IPR объясняет наблюдения или нет;
- изменение характеристики насоса согласуется с наблюдениями или нет.

PROSPER ранжирует модельные объяснения, но не доказывает, что физическая причина — износ, отложения, газ или конкретный отказ.

### GAP

Используется после выбора кандидатов из реестра возможностей:

- только для выбранных объектов разрешаются управляющие параметры;
- GAP подбирает точные значения частоты ЭЦН/скорости ШВН и других доступных контролей;
- проверяются интерференция, вода, минимальное забойное давление, давление в линии и ограничения сети;
- результат прогнозируется до конца суток или следующего 24-часового периода.

Реестр возможностей и GAP не дублируют друг друга: реестр говорит, где есть потенциал и при каких условиях, GAP определяет точный совместный режим.

## 6. Данные и состояние

- `data/mvp_day/` — учебный почасовой кейс с редкой телеметрией.
- `data/opportunity_register_structured.json` — структурированный реестр потенциалов.
- `config/` — ограничения, диагностические модели, повтор лицензии и ресурсный бюджет.
- `data/live/` — изменяемое состояние витрины, расчётные кэши и локальные решения. Каталог исключён из Git.
- `runtime/` — рабочие копии PetEx. Каталог исключён из Git.
- `IM_2022_06/` — исходные модели PetEx только для чтения; каталог исключён из Git.

Чёрная плитка в визуализации — модуль невязки между суммой оценок скважин и фактом сепаратора. Это не отдельная скважина и не автоматическая локализация потери.

## 7. Ключевые состояния

- `needs_data` — свежих корректных данных недостаточно; расчёт не запускается.
- `running` — выполняется Codex или расчётный инструмент.
- `waiting_license` — лицензия недоступна; показана следующая попытка.
- `needs_attention` — автоматическое восстановление небезопасно или расчёт завершился ошибкой.
- `awaiting_human_decision` — есть готовое предложение, требуется решение инженера.
- `awaiting_revision_calculation` — инженер вернул предложение с комментарием.
- `approved_for_execution` — решение утверждено и может имитироваться локально.
- `closed_rejected` — предложение отклонено.

## 8. Текущая готовность

Реализованы:

- почасовая витрина и два учебных инцидента;
- динамический контроль допуска ±5%;
- редкая телеметрия и несколько кандидатов/гипотез;
- автономный вызов Codex CLI;
- базовые проверки и модельная диагностика PROSPER;
- выбор мероприятий из реестра и расчёт GAP;
- сценарий кислотной промывки с длительностью этапов;
- расчёт остаточного недобора до конца суток;
- HITL: утверждение, отклонение и возврат на доработку;
- локальный реестр исполнения;
- повтор при недоступной лицензии;
- межпроцессные блокировки и атомарная запись состояния;
- 77 автоматических тестов.

Последний исправленный дефект: два перезапуска Streamlit могли одновременно заменить `data/live/lifecycle.json` и вызвать `WinError 5`. Теперь операции жизненного цикла сериализованы отдельной блокировкой, а атомарная замена имеет короткие повторы.

## 9. Известные ограничения

1. Автономность пока привязана к работе витрины: отдельный фоновый почасовой процесс не завершён.
2. Подтверждение фактического эффекта после исполнения ещё недостаточно развито.
3. Экономическое и ресурсное ранжирование мероприятий пока упрощено.
4. Планировщик может перейти от трёх предложенных LLM наборов к проверке всей доступной регулирующей способности. Это прозрачно показано, но нужен более селективный поиск лучшего набора.
5. Не все физические причины можно различить имеющимися измерениями. Система обязана показывать неопределённость, а не придумывать диагноз.
6. Восстановление после аварии Codex/PetEx реализовано частично; неизвестное состояние прежнего вызова намеренно требует внимания человека.
7. Интерфейс содержит предупреждения Streamlit о будущем удалении `use_container_width`; это не функциональная ошибка, но технический долг.

## 10. Рекомендуемые следующие задачи

Порядок важен:

1. Сделать устойчивый прогон обоих инцидентов от 00:00 до конца суток без ручного вызова агента.
2. Проверить, что второй инцидент независимо создаётся, рассчитывается и получает собственное решение.
3. Добавить подтверждение/неподтверждение ожидаемого эффекта по новым фактическим данным.
4. Отделить фоновый почасовой цикл от Streamlit, оставив витрину только интерфейсом наблюдения и HITL.
5. Сделать селективный поиск наборов мероприятий перед GAP с явной целевой функцией и масштабируемым бюджетом расчётов.
6. Расширить ресурсные и экономические ограничения, включая выезд бригады и длительность ГТМ.
7. Только после стабильного MVP добавить выключенный по умолчанию адаптер создания задачи в Битрикс.

## 11. Как проверять изменения

```powershell
python -m unittest discover -s tests -q
python -m streamlit run dashboard.py --server.port 8503
```

Для интерфейса пройди минимум следующие точки:

- 00:00 — нормальный режим;
- 06:00 — первый выход за допуск, диагностика и готовое решение;
- утверждение и почасовое применение эффекта;
- второй инцидент — отдельная карточка, отдельные гипотезы и решение;
- отсутствие свежего факта;
- недоступная лицензия и автоматическая повторная попытка;
- возврат на доработку с комментарием.

Реальный PROSPER/GAP запускать только после проверки лицензий, отсутствия чужих процессов и наличия рабочей копии модели.
