# Инструкции для Claude Code

Перед изменениями прочитай:

1. `AGENTS.md` — обязательные правила работы и безопасности.
2. `docs/CLAUDE_HANDOFF.md` — инженерный контекст, устройство системы и текущее состояние.
3. `README.md` — запуск и обзор репозитория.
4. `PROJECT_PROGRESS.md` — подробная история решений; используй как журнал, а не как актуальный список задач.

## Как работать с пользователем

- Пользователь — инженер по интегрированному моделированию с навыками программирования, не профессиональный разработчик.
- Объясняй результат простым инженерным языком: сначала что изменилось и зачем, затем технические детали.
- Не спрашивай подтверждение каждого мелкого шага. Самостоятельно выполняй безопасные действия в рамках поставленной задачи.
- Не усложняй архитектуру без необходимости. Сначала простое проверяемое решение, затем развитие.
- Не добавляй LLM туда, где достаточно формулы, правила, проверки данных или готового расчётного инструмента.

## Неприкосновенные правила

- Не читать и не изменять `C:\work-scripts\Pssport_IMA` без нового явного разрешения пользователя.
- `IM_2022_06` — исходные модели только для чтения. Расчёты и сохранение выполнять исключительно на копиях в `runtime/`.
- Не запускать параллельно несколько PROSPER/GAP/OpenServer-процессов. Перед запуском проверить активные процессы и проектную блокировку.
- Не закрывать процессы PetEx, которые могли быть запущены пользователем.
- Не утверждать решение за инженера и не выполнять реальных внешних действий.
- Битрикс выключен. На стадии MVP внешнее действие — только локальная запись.
- Нет свежего корректного факта — нет инцидента, диагностики и оптимизации.
- Не выдавать эвристику, интерполяцию старых кривых или телеметрический признак за результат PROSPER/GAP.

## Инженерная логика, которую нельзя потерять

- Потеря на сепараторе обнаруживает проблему, но сама по себе не локализует скважину.
- Кандидаты формируются по доступной телеметрии; отсутствие аномалии не доказывает исправность скважины.
- PROSPER проверяет согласованность гипотез по притоку и лифту. Он не доказывает физическую причину отказа.
- Реестр возможностей содержит потенциалы и условия достижения, но не обязан содержать точные новые режимы.
- LLM предлагает осмысленные наборы мероприятий из реестра.
- GAP рассчитывает точные управления выбранных объектов и проверяет интерференцию и ограничения сети.
- Цель текущего кейса — минимизировать недобор к концу суток/24-часового горизонта. Если полностью закрыть его невозможно, нужен лучший допустимый вариант с честно показанным остатком.
- Любое предложение ожидает решения инженера (HITL).

## Рабочий порядок

1. Перед изменениями посмотри `git status` и не затирай чужие правки.
2. Для поиска используй `rg`/`rg --files`.
3. Меняй код небольшими связными порциями.
4. Добавляй тест на найденную ошибку или новое правило.
5. Минимальная проверка: `python -m unittest discover -s tests -q`.
6. Для изменений интерфейса дополнительно проверь реальную страницу Streamlit на `http://127.0.0.1:8503/`.
7. Не запускай реальный PetEx только ради проверки интерфейса или документации.
8. Запиши существенный итог и оставшиеся ограничения в `PROJECT_PROGRESS.md`.

## Что считать завершением задачи

- Код соответствует инженерной логике, а не только демонстрационному сценарию.
- Изменённые входные данные обрабатываются тем же алгоритмом без привязки к номеру инцидента или конкретной скважине.
- Ошибки лицензии, нехватка данных и прерванные расчёты показаны пользователю понятным статусом.
- Тесты проходят; интерфейс не содержит технической трассировки вместо понятного сообщения.
- Результат не заявлен подтверждённым, если соответствующий инструмент фактически не запускался.
